# Gyeonggi Partners: Proposal Relay Editing & Voting System

이 문서는 경기 파트너스 프로젝트의 핵심 기능인 **제안서 릴레이 공동 편집 및 투표 시스템**의 비즈니스 로직과 사용자 시나리오를 정의합니다.
이 파일을 읽는 AI 모델은 아래 명세된 기능만을 구현해야 하며, 명시되지 않은 부가 기능(알림, 포인트, 히스토리 등)을 임의로 추가해서는 안 됩니다.

---

## 1. 시스템 개요 및 목표
- **목표**: 논의방 내 참여자들이 릴레이 방식(비관적 락 활용)으로 하나의 제안서를 공동 작성하고, 투표를 통해 최종 안건으로 확정하는 시스템.
- **핵심 가치**: 동시성 제어를 통한 데이터 정합성 보장, 명확한 상태 관리에 따른 편집 권한 제어.

---

## 2. 핵심 용어 및 상태 정의

### 2.1. 상태(ProposalStatus)
제안서의 생명주기는 아래 상태값에 따라 관리됩니다.
1. **DRAFTING (작성 중)**: 특정 사용자(작성자)가 편집 락(Lock)을 소유하고 수정 중인 상태.
2. **SAVING (임시 저장)**: 편집이 종료되어 내용이 저장된 상태. 락이 해제되어 있어 누구나 편집 모드로 진입 가능.
3. **COMPLETED (확정)**: 내용 작성이 완료되어 더 이상 수정할 수 없는 불변(Immutable) 상태.
4. **VOTING (투표 중)**: 확정된 제안서에 대해 찬성 투표가 진행 중인 상태.
5. **READY_TO_SUBMIT (제출 대기)**: 투표 기간 만료 또는 최소 인원 달성으로 인해 투표가 종료된 상태.
6. **SUBMITTED (제출 완료)**: 외부 시스템으로 이관된 상태.

### 2.2. 락(Lock) 매커니즘
- **물리적 락 (DB Lock)**: `PESSIMISTIC_WRITE` (비관적 락). 편집 모드 진입(`startEditing`) 시점의 동시성 제어를 위해 찰나의 순간 사용.
- **논리적 락 (App Lock)**: `locked_by` 컬럼. 사용자가 편집을 시작하면 ID를 기록하고, 편집을 종료(`stopEditing`)하거나 완료(`complete`)할 때까지 장기간 유지됨.

## 3. 상세 동작 시나리오 (User Scenarios)

### Scenario 1: 제안서 생성 및 독점권 획득
- **Action**: 사용자 A가 논의방에서 '제안서 생성'을 요청한다.
- **System**:
    1. 제안서 데이터를 생성하고 초기 상태를 `DRAFTING`으로 설정한다.
    2. A를 즉시 `locked_by`에 등록하여 편집 권한을 부여한다.
- **[Out of Scope]**: 생성 알림 발송, 포인트 지급.

### Scenario 2: 임시 저장 및 권한 반납
- **Action**: 사용자 A가 작성을 멈추고 '임시 저장 후 나가기'를 요청한다.
- **System**:
    1. 변경된 제목, 본문, 증거자료를 업데이트한다.
    2. 상태를 `SAVING`으로 변경한다.
    3. `locked_by`를 `NULL`로 초기화하여 락을 해제한다.
- **[Out of Scope]**: 저장 완료 시스템 메시지 기록, 버전 관리(History).

### Scenario 3: 릴레이 편집 모드 진입
- **Action**: 사용자 B가 `SAVING` 상태의 제안서를 보고 '수정하기'를 요청한다.
- **System**:
    1. DB 비관적 락으로 동시 진입을 차단한다.
    2. 상태를 `DRAFTING`으로 변경한다.
    3. `locked_by`를 B로 갱신하고, `last_modifier`를 B로 업데이트한다.
- **[Out of Scope]**: 이전 작성자에게 알림 발송.

### Scenario 4: 내용 수정 (중간 저장)
- **Action**: 락을 가진 사용자 B가 내용을 수정하고 '저장'을 요청한다.
- **System**:
    1. 데이터를 DB에 업데이트한다.
    2. `DRAFTING` 상태와 `locked_by` 정보는 그대로 유지한다. (편집 모드 유지)

### Scenario 5: 작성 완료 (확정)
- **Action**: 사용자 B가 작성을 마치고 '작성 완료'를 요청한다.
- **System**:
    1. 상태를 `COMPLETED`로 변경한다.
    2. `locked_by`를 영구적으로 `NULL` 처리한다.
- **Constraints**: 이후 누구도 내용을 수정할 수 없다.

### Scenario 6: 투표 시작 설정
- **Action**: 확정된 제안서에 대해 사용자 B가 투표 조건(최소 인원, 마감 기한)을 입력하고 투표 시작을 요청한다.
- **System**:
    1. 입력값을 저장하고 상태를 `VOTING`으로 변경한다.
    2. 마감 기한은 반드시 미래 시간이어야 한다.

### Scenario 7: 투표 참여 (동의)
- **Action**: 사용자 C, D가 투표 중인 제안서에 '동의'한다.
- **System**:
    1. 중복 투표 여부를 검증한다.
    2. 동의 내역(`ProposalConsent`)을 저장한다.
    3. **조건 달성 체크**: 동의 후 최소 인원을 달성했는지 확인하고, 달성 시 즉시 `READY_TO_SUBMIT`으로 상태를 변경한다.

### Scenario 8: 투표 자동 종료 (시간 만료)
- **Condition**: 제안서가 `VOTING` 상태이나 마감 기한이 경과함.
- **System (Scheduler)**:
    1. 주기적으로 만료된 제안서를 감지한다.
    2. 상태를 `READY_TO_SUBMIT`으로 일괄 변경한다.

### Scenario 9: 단순 조회
- **Action**: 논의방 멤버가 제안서를 조회한다.
- **System**: 최신 데이터를 반환한다. 작성 중인 경우 `locked_by` 정보를 포함하여 클라이언트가 '수정 불가' 상태임을 알 수 있게 한다.

## 4. 기술적 제약사항 (Technical Constraints)
1. **Concurrency**: Redis를 사용하지 않고, 오직 RDBMS의 기능(Transaction, Lock)과 애플리케이션 로직으로 동시성을 제어한다.
2. **Persistence**: DDD 원칙에 따라 도메인 모델(POJO)과 영속성 엔티티(@Entity)를 분리하며, 상태 변경 시 반드시 `repository.save()`를 호출하여 Dirty Checking의 한계를 보완한다.
3. **Validation**: 편집 진입(`startEditing`) 시 상태(`status`)를 먼저 검증하여, `VOTING`, `COMPLETED` 등의 상태에서는 편집을 원천 차단한다.
